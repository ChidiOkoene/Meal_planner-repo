# @dyjext/db

Prisma schema, migrations and seed data for PostgreSQL 16. See `docs/ARCHITECTURE.md` §7.

## Usage

```ts
import { createPrismaClient, RecipientStatus } from '@dyjext/db';

const prisma = createPrismaClient(); // reads DATABASE_URL
const active = await prisma.recipient.findMany({ where: { status: RecipientStatus.active } });
```

Create one client per process and call `prisma.$disconnect()` on shutdown.

## Conventions

Every model follows the rules at the top of `prisma/schema.prisma`: UUIDv7 ids, snake_case in the database, `timestamptz` timestamps, and money as integer minor units plus a currency code.

## Changing the schema

1. Edit `prisma/schema.prisma`, with a `///` comment on every new model.
2. Run `pnpm db:migrate` from the repository root and name the migration.
3. Commit the schema and the new folder under `prisma/migrations/` together.

CI applies all migrations to a fresh database and fails if the schema and migrations disagree (`pnpm db:check`).

## Notes

- Prisma 7 needs a driver adapter; `createPrismaClient` uses `@prisma/adapter-pg`.
- The generated client lives in `src/generated/` and is not committed. Builds regenerate it.
- Ids are generated by Prisma, not by a database default, so raw SQL inserts must supply one.

## Sample catalogue

`pnpm db:seed` loads a **development-only** sample of 46 ingredients and 32 Nigerian dishes (`prisma/seed-data/catalogue.ts`). Nutrient values are rounded approximations stored with source `estimate`, and every dish is a `draft`. They exist so the planner can be built and demonstrated; they must not be used for real recipients. Issue #12 replaces them with sourced, dietitian-verified data.

## Dish versions

Versions of a dish share a `familyId` (the id of version 1). A verified version is never edited: changing it creates the next version as a draft, and the planner keeps using the latest verified version until the new one is verified. See `CatalogueService` in `apps/api`.
